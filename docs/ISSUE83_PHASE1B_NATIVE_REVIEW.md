# Issue 83 Phase 1B native-wheel review

Status: **in progress; Phase 1B has not passed its gate** (September 28, 2026). This record covers a local Windows x64 CPython 3.13.15 probe and source/notice findings. It does not approve a processing payload or change the Python-only installer.

## Hash-checked CPU-only CTranslate2 candidate

The upstream `ctranslate2-4.8.1-cp313-cp313-win_amd64.whl` has SHA-256 `d52499f05a60a791aeadee28d609efa130142f376d1ea76b2b1c593bb01f8827` in the [26-wheel candidate manifest](ISSUE83_WHEEL_CANDIDATES.json). It contains `ctranslate2/cudnn64_9.dll` (266,288 bytes; SHA-256 `9edbcdff73b0af070eb160b2ce66e59feca04aa017351d8eedcc5e8e149967d2`), but no wheel license/notice file. The tagged [v4.8.1 source archive](https://github.com/OpenNMT/CTranslate2/releases/tag/v4.8.1) downloaded from GitHub's codeload endpoint is 3,431,585 bytes, SHA-256 `05c4e8a42c8573d0c79782e8408037c16db143334b6f4ee1cef23aa3b08a4dfa`; it contains the project's MIT `LICENSE`, build recipe, and `.gitmodules`, but not the submodule contents.

The tag's `python/tools/prepare_build_environment_windows.sh` builds with `WITH_CUDA=ON`, `CUDA_DYNAMIC_LOADING=ON`, `WITH_CUDNN=OFF`, and `WITH_DNNL=ON`; it then copies `cudnn64_9.dll` into the wheel from the installed CUDA/cuDNN toolchain. Thus omitting that one copied DLL is consistent with the tagged build's cuDNN-disabled configuration, but the resulting wheel still contains CUDA-capable code. This implements Phase 0's exclusion of optional GPU **runtime payloads**, not a new promise to remove every GPU interface. The source recipe references CUDA 12.8.1, cuDNN 9.10.2, Intel oneAPI/MKL 2025.3.0, and oneDNN 3.1.1. Those inputs and the source code actually compiled into the binary still require a complete license/build-material map.

The [candidate transformation](../scripts/issue83_cpu_wheel.py) verifies the exact upstream wheel hash, the cuDNN member hash, and every original `RECORD` entry; it writes a new wheel without that member and rewrites `RECORD`. It refuses an existing destination and leaves the upstream wheel untouched. Two independent local transformations produced the same SHA-256 `fbd36827cafdf111a60211d4a361177574c13e597083b92a57c7941f9e31182d`. Five synthetic regression tests passed, including wrong hash, wrong `RECORD`, missing member, existing output, and deterministic output. Phase 3 must still compare the staged and installed payloads against the approved omission and assert that no unreviewed GPU runtime was added.

All 26 cached candidate wheel SHA-256 values were rechecked. Their 31 active dependency edges have no missing or unsatisfied version constraints under the candidate target environment. A fresh, ignored scratch target under the official full private Python 3.13.15 installed the 25 original wheels and transformed CTranslate2 wheel offline. Both the installed DLL tree and installed CTranslate2 `RECORD` omit cuDNN. The [runtime probe](../scripts/probe_issue83_runtime.py) reported no bundled cuDNN DLL, imported the native stack, decoded 10 synthetic H.264 frames and 32,000 audio samples, and completed an offline `large-v3` CPU `int8` inference using the existing cached model. This verifies local execution, not transcription accuracy or clean-host installer readiness. Pip's 26.2.1 bootstrap is separate from these 26 processing wheels and must appear in the final input lock/notice map.

The wheel's `libiomp5md.dll` (SHA-256 `982233366b0afcda1e0f55a0b134097e35b779613f54ddb69e685e6cd06b755f`) is byte-identical to the DLL in Intel's [2025.3.0 Windows OpenMP wheel](https://pypi.org/project/intel-openmp/2025.3.0/) (wheel SHA-256 `8ff899d01a41b92ffe0e618b221ea633127d16df726086082d381c431c31339d`). That wheel includes an Intel Developer Tools EULA and OpenMP `third-party-programs.txt`; the latter refers to a separate oneTBB notice. This is an exact binary/notice lead, **not** a determination that the project may redistribute the DLL or that the notice set is complete. Intel's [deployment guidance](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2023-2/redistribute-libraries-when-deploying-apps.html) directs distributors to inspect the applicable license and third-party files for redistributable components. A version-matched redistribution designation and the referenced nested notice remain open.

MinGW `objdump -p` on the wheel's `ctranslate2.dll` found imports of its packaged `libiomp5md.dll`, `MSVCP140.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`, and Windows/UCRT system DLLs. `_ext.cp313-win_amd64.pyd` also imports `MSVCP140.dll`, `VCRUNTIME140.dll`, `python313.dll`, and `ctranslate2.dll`. The official private Python archive carries the `VCRUNTIME140` DLLs but not the `MSVCP140` family; this machine's successful import may rely on its installed Microsoft C++ runtime. [CTranslate2's hardware guide](https://github.com/OpenNMT/CTranslate2/blob/v4.8.1/docs/hardware_support.md) specifies x86-64 CPUs with at least SSE 4.1 for its prebuilt wheels. Resolve the Microsoft runtime's exact app-local/prerequisite treatment and its redistribution terms before declaring a clean-host-ready lock. Actual clean-host testing remains Phase 7.

Two PyPI wheels without source distributions now have verified matching tagged source paths: [faster-whisper v1.2.1](https://github.com/SYSTRAN/faster-whisper/releases/tag/v1.2.1) source archive SHA-256 `ff0b5428b3a074cd63f580ae73fa21f7d9fd3bba28e0e2e097868d78d5b06f2f` (all 9 shipped `.py` files byte-identical), and [FlatBuffers v25.12.19](https://github.com/google/flatbuffers/releases/tag/v25.12.19) source archive SHA-256 `f81c3162b1046fe8b84b9a0dbdd383e24fdbcf88583b9cb6028f90d04d90696a` (all 10 shipped `.py` files byte-identical). Their top-level `LICENSE` files are present in the tagged archives. These matches do not clear their transitive dependencies.

The [ONNX Runtime v1.29.0 tag](https://github.com/microsoft/onnxruntime/releases/tag/v1.29.0) source archive is 277,662,433 bytes, SHA-256 `0f065cfd3816eaa4b709a057ea0e237ebc6463843af44a439e0d81af76d6620e`. Its `LICENSE` and `ThirdPartyNotices.txt` match the corresponding files inside the Windows wheel after CRLF-to-LF normalization. The source archive contains `.gitmodules`; it does not by itself prove the exact compiled dependency set or supply every nested source required by those notices. MinGW import inspection of the wheel's `onnxruntime.dll` also found `MSVCP140.dll`, `MSVCP140_1.dll`, and `VCRUNTIME140` dependencies; the applicable notice/build-input mapping for its three native files remains open.

The published PyAV 18.1.0 wheel's FFmpeg binaries trace to the tagged [pyav-ffmpeg `8.1.2-1` build recipe](https://github.com/PyAV-Org/pyav-ffmpeg/releases/tag/8.1.2-1); its locally downloaded tag archive is SHA-256 `a3bd63dba5336ec47766f8e59ba065d16342002d922c2f96cfed9d1a9b6da6d8`. The tagged `scripts/pkg.py` pins source URLs and SHA-256 values for FFmpeg 8.1.2, x264, x265, LAME, Opus, dav1d, SVT-AV1, libvpx, libpng, libwebp, opencore-amr, libvpl, and build/header inputs. Its Windows configuration enables both `libx264` and `libx265` plus the other codec libraries and `libvpl`; it does not select the Linux-only GnuTLS group. This is a usable source map for investigation, but the current wheel contains 74 native `.pyd`/DLL files and its single PyAV BSD license file is insufficient for the bundled FFmpeg/native payload. Only 11 wheel DLLs have so far matched the upstream FFmpeg binary archive byte-for-byte, as recorded in the [local probe](ISSUE83_PHASE1_LOCAL_PROBE.md). The other wheel transformations, compiler inputs, exact notices, and GPL/LGPL obligations remain unresolved.

## Remaining Phase 1B gate

- Finish the source/notice/build-material mapping for PyAV's GPL-enabled FFmpeg/x264/x265 and other native DLLs. The published PyAV wheel's own BSD notice does **not** cover them. Path A remains provisional; the applicable in-process GPL obligations and compatibility of the Python processing program need review before release locking.
- Resolve the Intel OpenMP/oneMKL/oneDNN notice and redistribution chain for CTranslate2, including any statically linked code. If the published wheel cannot be cleared, choose and prove a narrower CPU-only build with reviewed replacement libraries; do not relabel the current wheel as open-source-only.
- Map ONNX Runtime, NumPy/OpenBLAS, tokenizer/HF-Xet native code, compiler runtimes, setuptools/pip vendors, and the remaining wheel notices to exact sources and applicable terms. The [candidate manifest](ISSUE83_WHEEL_CANDIDATES.json) is an inventory of filenames and metadata, not a complete legal notice set or approved input lock.
- Resolve `MSVCP140.dll` and `MSVCP140_1.dll` on the supported clean host and record the chosen OS/CPU baseline. Phase 3 verifies the staged no-cuDNN payload; Phases 6-7 verify the actual installer and clean host.

Therefore the Phase 1B gate is **open**. No modified wheel, native DLL, or processing package has been added to the installer.
