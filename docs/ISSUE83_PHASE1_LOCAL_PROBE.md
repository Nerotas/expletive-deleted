# Issue 83 local Python 3.13 processing probe

Status: **functional prototype passed; release input gate still open** (September 28, 2026). The maintainer chose provisional path A: investigate distribution of the published GPL-enabled PyAV wheel with the corresponding GPL obligations, while retaining MIT licensing for the project's own source where applicable. This is not final legal approval or a selection of the complete release payload.

## Isolated inputs

- Official Windows x64 CPython 3.13.15 embeddable zip, [Python release page](https://www.python.org/downloads/release/python-31315/), SHA-256 `d1f04d990aee1253d8569e8e5104e30fa9f5fa830899f14843448872d936a2cf`. This supplies the target interpreter ABI for a local probe; the production release workflow uses an installed Python 3.13.15 runtime, which still needs separate testing.
- pip 25.2 wheel, SHA-256 `6d67a2b4e7f14d8b31b8b52648866fa717f45a1eb70e83002f4331d07e953717`, bootstrapped only inside the ignored scratch runtime.
- All 26 downloaded [candidate wheels](ISSUE83_WHEEL_CANDIDATES.json), installed offline with `--no-index --only-binary=:all:` into ignored scratch. No system Python, current `.venv`, installer, or user media was modified. The normal sandbox blocked pip's temporary directories (`WinError 5`); installation and read-only native imports succeeded with a workspace-scoped unsandboxed run. This is a local environment limitation, not a dependency failure.
- Synthetic H.264 MP4 from the earlier forced `libx264` probe, SHA-256 `eb71fffaa166f9eab04441fb4097d1399cb2280931e382446237202479b66d00`; synthetic two-second 440 Hz WAV, SHA-256 `ede205dd7ba2e16a9ee1f1fecbc0be20f249c1caa52954112d8a7c41e6cd4be8`. Both are ignored scratch fixtures, not personal media or release assets.
- Existing locally cached `Systran/faster-whisper-large-v3` model snapshot. The inference probes used its direct path and `local_files_only=True`; no model download was performed.

## Results

Using the isolated Python 3.13.15 runtime, PyAV 18.1.0, CTranslate2 4.8.1, faster-whisper 1.2.1, NumPy 2.5.2, ONNX Runtime 1.29.0, and tokenizers 0.23.1 imported. CTranslate2 reported CPU compute types `float32`, `int8`, and `int8_float32`. PyAV decoded 10 H.264 video frames at 128×72. `faster_whisper.audio.decode_audio` returned 32,000 non-silent 16 kHz samples from the synthetic WAV. Offline CPU `large-v3` inference (`int8`, four CPU threads, beam size one) completed on that two-second input and produced one segment. This demonstrates execution, not transcription accuracy on speech.

The published CTranslate2 wheel contains `cudnn64_9.dll`, so **that wheel remains outside the approved CPU-only release scope as shipped**. For a temporary local probe, that one DLL was moved aside inside the ignored scratch install, the same CPU compute-type and offline `large-v3` inference checks passed, and the DLL was restored and verified afterward (SHA-256 `9edbcdff73b0af070eb160b2ce66e59feca04aa017351d8eedcc5e8e149967d2`). No `cudnn64_9.dll` was found on `PATH`. This supports investigating an audited staging transformation that omits optional cuDNN, but it is not yet proof of a clean-host package, absence of every GPU runtime, or a complete native-library/license inventory.

PyAV's wheel also carries `av.libs/libvpl-969a52d626b0390fc34f6a4fb0b08d7e.dll` (SHA-256 `96a2ee0b9d4645791485f0f897fd4ea4d77f324e11918dbc10466fc949f7dca4`). [Intel describes libvpl as a dispatcher](https://github.com/intel/libvpl), distinct from the separately installed GPU implementation. The [pinned PyAV FFmpeg recipe](https://github.com/PyAV-Org/pyav-ffmpeg/blob/8.1.2-1/scripts/build-ffmpeg.py) enables `--enable-libvpl` for Intel Quick Sync, and its [source recipe](https://github.com/PyAV-Org/pyav-ffmpeg/blob/8.1.2-1/scripts/pkg.py) names libvpl v2.16.0 with source-archive SHA-256 `d60931937426130ddad9f1975c010543f0da99e67edb1c6070656b7947f633b6` (upstream recipe value, not independently rehashed here). In a local omission test, removing this DLL from the isolated scratch installation made `import av` fail with a DLL-load error; it was restored with the same hash. Thus the published wheel cannot simply omit the dispatcher. The Phase 0 exclusion of optional **GPU runtimes** is not automatically violated by a dispatcher, but its exact source/notice and any runtime-loading behavior still belong in the native-library audit. A stricter no-GPU-interface policy would require a different/rebuilt PyAV wheel; no such policy change is inferred here.

The reusable [runtime probe](../scripts/probe_issue83_runtime.py) checks imports, CPU compute types, synthetic video/audio decoding, and optionally an offline cached-model inference. It prints counts and versions, not transcript contents. Its `--require-no-cudnn` mode can check a future staged payload that actually omits the DLL.

## PyAV/FFmpeg upstream build anchor

The inspected PyAV wheel SHA-256 `ea1480b7a8d5405cb5f382b344731bf125fd2c1c6fae3964f6c48595628387ff` also matches the Windows x64 asset of [PyAV v18.1.0](https://github.com/PyAV-Org/PyAV/releases/tag/v18.1.0), commit `7e3d950a8b72062502c1a60d672f8ca565313af5`. That tag's `scripts/ffmpeg-latest.json` points to [pyav-ffmpeg 8.1.2-1](https://github.com/PyAV-Org/pyav-ffmpeg/releases/tag/8.1.2-1), commit `a71bf9279f7a4659154b68ba6783e89be460bcd5`. Its Windows x64 FFmpeg binary archive was downloaded and verified at SHA-256 `d00e5c5ae01d5c51dd56043bc9597d9d03200ab72695e1b61565b75f02a2e380`.

Eleven DLLs inside the PyAV wheel are byte-identical to files in that upstream FFmpeg archive, including `libx264-165.dll`. The remaining DLLs are not byte-identical and have not yet been traced through the wheel-packaging transformation; any explanation for those differences is still an inference. At the [pinned upstream build recipe](https://github.com/PyAV-Org/pyav-ffmpeg/blob/8.1.2-1/scripts/pkg.py), FFmpeg source is `ffmpeg-8.1.2.tar.xz` (SHA-256 `464beb5e7bf0c311e68b45ae2f04e9cc2af88851abb4082231742a74d97b524c`) and x264 source is commit `b35605ace3ddf7c1a5d67a2eb553f034aef41d55` (archive SHA-256 `6eeb82934e69fd51e043bd8c5b0d152839638d1ce7aa4eea65a3fedcf83ff224`). This establishes a strong candidate build chain, **not** a complete source companion: the FFmpeg archive contains binaries, headers, and libraries but no full third-party license/notice files, and its other dependencies, patches, compiler inputs, and wheel transformations still need a release-specific map.

## Remaining work by gate

1. Review path A's actual in-process Python program and corresponding-source obligations; map the exact PyAV/FFmpeg/x264 and other native binaries to source, build inputs, notices, and compatible terms. The published wheel's BSD metadata alone does not describe its GPL-enabled FFmpeg DLLs.
2. Select a source-complete GPL FFmpeg/FFprobe/x264 executable build, or produce a pinned build; map yt-dlp's embedded dependencies, Deno, CPython, and pip. The tested BtbN executable is a functional candidate, not a release selection.
3. For Phase 1B, select and locally prove a reproducible cuDNN omission or CPU-only CTranslate2 build; review its other native libraries, including PyAV's required oneVPL dispatcher, and distinguish dispatchers/headers from GPU runtimes. Phase 3 must audit the actual assembled cuDNN-free payload, including installed metadata and output inventory.
4. After integration, Phase 3 tests the staged runtime under the actual private Python, Phase 6 audits the installer and release assets, and Phase 7 installs and tests the real package on clean Windows x64 without separately installed processing/GPU tools. Keep the model as an explicit first-run download, and retain the separate codec-patent release decision.

No production packaging or dependency policy was changed by this probe.
